# UX_transaction-search: Transaction search

**Status**: Implemented <!-- Draft -> Options Presented -> Selected -> Ready for Dev -> Implemented -->
**Created**: 2026-09-11
**Last updated**: 2026-09-11 (Implemented)
**Direction**: [ux/UX_DIRECTION.md](UX_DIRECTION.md) - "Calm Ledger", Ready for Dev

## Page
`transaction-search` (`finance-manager-ui/src/app/transaction-search/`) - originally routed at `/tabs/transactions/search`, reached via a filter icon in `transaction-list`'s header (see JIRA_14, the component-split ticket this page came from). Covers only the query-defining filters: date range, account selector + modal, category selector + modal, DR/CR selector. The batch-categorize toolbar is explicitly out of scope - it stayed on `transaction-list` (see JIRA_14's Implementation notes for why) and this round doesn't touch it.

**Option 4 (added on request, then refined) changes how `transaction-search` and `transaction-list` are composed, not whether they're separate components.** First cut: put the filters back on the same page by merging `transaction-search` into `transaction-list` outright - rejected on clarification, since that throws away JIRA_14's actual goal (keeping the filter logic and the row-rendering logic in separate, independently-testable components). **Refined design**: a new wrapper component hosts both `transaction-search` and `transaction-list` as literal template children on one page - real `@Input`/`@Output` bindings between them (the "parent container" pattern originally chosen for JIRA_14's communication mechanism, now usable directly since both live under the same parent instead of on separate routes coordinated through a router-outlet). `TransactionsShellComponent` (the router-outlet-`(activate)` coordinator JIRA_14 built specifically because the two were on separate routes) is no longer needed and gets deleted along with the `/tabs/transactions/search` child route - `transactions` goes back to being a single leaf route, now loading the new wrapper instead of `TransactionListComponent` directly. See Implementation detail for the exact shape. Also on request: the live text-search bar's look is revamped (see Option 4's note).

## Options presented

Real data pulled via `db-run`, and it directly illustrates JIRA_13's driving complaint (density/clutter):
- **Accounts**: `user_account` for `user_id=1` returns **39 rows** - only 6 are real (`HDFC RISHI`, `ICICI RISHI`, `SARASWAT RISHI`, `CANARA RISHI`, `AXIS RISHI`, `GROWW`), the other 33 are accumulated BDD/UI-test noise (`TJSB backend test <epoch>`, `TJSB UI test <epoch>`, `TJSB UI renamed <epoch>`). The current account-selector modal would show all 39 in one flat, ungrouped list today - this is a concrete, real demonstration of why the filter screen feels cluttered, not a hypothetical.
- **Categories**: `user_category` for `user_id=1` returns **214 rows** - only 5 are real (`SALARY`, `FOOD`, `LUNCH`, `DINNER`, `SNACKS`), the other 209 are `TEST_CAT_*`/`TEST_CAT_RENAMED_*` noise from BDD runs (same pollution pattern already documented in `ux/UX_category-list.md`).
- Mockups use the 6 real accounts and 5 real categories as the happy-path content (matching every prior round's convention of showing real, not fabricated, data) while explicitly designing the account/category pickers to scale to the real 39/214-row reality, not just the clean 6/5.

Artifact: [Transaction Search Layout Options](https://claude.ai/code/artifact/e96870bb-2d78-4a1c-93c6-23fa7d872c0d)

### Option 1 - Compact single-row filter bar
- **Artifact**: [Transaction Search Layout Options](https://claude.ai/code/artifact/e96870bb-2d78-4a1c-93c6-23fa7d872c0d) (row 1)
- **Layout**: all four filters (dates, accounts, categories, DR/CR) stay in one horizontal row exactly like today's structure, but tightened: shorter labels, no per-field stacked label above input (label moves inline/as placeholder), tighter gaps. The account/category pickers themselves are unchanged in this option - the density fix is only at the top-level row, not inside the modals. A single full-width "Apply" button anchors the bottom.
- **States covered**: happy (6 accounts/5 categories selectable), empty accounts/categories (a muted inline message replacing the picker row entirely, with a link to Accounts/Categories tabs), loading (a thin indeterminate bar under the header while accounts/categories are still being fetched), error (not really applicable here - this screen doesn't fetch transactions itself, just picks filters for the next fetch; no error state needed).

### Option 2 - Two-tier filter groups with grouped/searchable pickers
- **Artifact**: [Transaction Search Layout Options](https://claude.ai/code/artifact/e96870bb-2d78-4a1c-93c6-23fa7d872c0d) (row 2)
- **Layout**: splits the row into two visually distinct tiers - a top tier for "when" (date range) and a bottom tier for "what" (accounts, categories, DR/CR) - addressing density by giving each concern its own visual weight instead of five equal-width fields in one line. The account-selector modal adds a search bar at the top, matching the category modal's existing search. **Real finding while building this mockup**: grouping by `type_1`/`type_2` alone does *not* separate the 33 noise accounts from the 5 real ones - every `TJSB *` test account is also `cash`/`bank`, the same type as `HDFC`/`ICICI`/`SARASWAT`/`CANARA`/`AXIS`, so a type-based group would still be one 38-row "Cash" list. What actually helps in the mockup: alphabetical sort within the group, since none of the 5 real bank names start with "T" - the 33 `TJSB` entries naturally sort to the end, and the search bar (not the grouping) is what actually lets a user skip past them. The mockup reflects this honestly (one "Cash - 38 accounts" group, sorted, with a note) rather than pretending type-grouping alone solves the scale problem.
- **States covered**: happy (6/5 real items, grouped + searchable), empty (same inline message as Option 1), loading (same thin bar), error (n/a, same reasoning as Option 1).

### Option 3 - Chip-summary with drill-down
- **Artifact**: [Transaction Search Layout Options](https://claude.ai/code/artifact/e96870bb-2d78-4a1c-93c6-23fa7d872c0d) (row 3)
- **Layout**: the main screen shows only compact read-only summary chips ("Apr 1 - Mar 31", "3 accounts", "2 categories", "All") in a single row - tapping any chip opens that one filter's picker as a focused sheet (reusing Option 2's grouped+searchable account/category modals underneath). This is the most aggressive density fix - the top-level screen has almost nothing on it until you drill into a specific filter.
- **States covered**: happy (chips reflect current selection state, e.g. "6 accounts" once all are picked), empty (a chip reading "No accounts yet" that's disabled/muted rather than a full inline message, since there's less room for it), loading (chips show a muted "..." placeholder instead of a bar), error (n/a).

### Option 4 - Inline, filter and transactions on same page, components stay separate (added on request, refined on clarification)
- **Artifact**: [Transaction Search Layout Options](https://claude.ai/code/artifact/e96870bb-2d78-4a1c-93c6-23fa7d872c0d) (row 4)
- **Layout**: a condensed single-row filter bar (date range / accounts / category / DR-CR, styled like Option 1's tightened chips) sits directly above the transaction list on one continuous page - filters take effect via the existing header refresh action, matching the pre-JIRA_14 model. Below the filter row: a **revamped search bar** (see its own note below). Below that: the summary row and live transaction rows, unchanged from `transaction-list`'s current real content. **Visually this is one seamless page** - but underneath, `transaction-search` and `transaction-list` stay two separate components, composed by a new wrapper rather than merged into one. See Implementation detail for the exact component shape.
- **Real consequence found while building this**: because the transaction list is on the same page, this option **needs an error state that Options 1-3 don't** - the page now fetches transactions itself (the fetch that's genuinely reachable, per `ux/UX_transaction-list.md`'s Implementation notes), so a real "couldn't load transactions" state has to exist here, unlike the filter-only screen.
- **States covered**: happy (filters + revamped search bar + real transaction rows together), error (new, see above), empty (no accounts selected), loading (skeleton rows below the filter bar, matching `transaction-list`'s existing skeleton pattern).

## Selected option
**Option 4 - Inline, filter and transactions on same page, components stay separate**, confirmed by the user, then refined: the first cut (fold `transaction-search` into `transaction-list` outright) was rejected on clarification - the components stay separate, only how they're *composed* changes. See Implementation detail for the corrected shape.

## Implementation detail

Grounded against the real, already-split `finance-manager-ui/src/app/transaction-search/`, `transactions-shell/`, and the trimmed `transaction-list/` (all from JIRA_14):

1. **New wrapper component replaces the router-outlet coordination, doesn't undo the split.** `TransactionsShellComponent` exists today specifically to coordinate `transaction-search` and `transaction-list` across two separate *routes*, via `<ion-router-outlet>`'s `(activate)` event - a workaround needed only because the two components weren't template siblings. With both now living on the same page, that workaround is unnecessary: a new wrapper component (name TBD at implementation time, e.g. `TransactionsPageComponent`) templates both directly - `<app-transaction-search>` then `<app-transaction-list>` - and wires them with plain `@Input`/`@Output`, the same mechanism JIRA_14 originally chose before "separate route" made it need the router-outlet detour. `TransactionsShellComponent` and the `/tabs/transactions/search` child route both get deleted; `tabs.routes.ts`'s `transactions` entry goes back to a single leaf route, now loading the new wrapper instead of `TransactionListComponent` directly. **This is still a real structural change** - new component, deleted component, changed routes - not a pure `ux-apply` restyle; flag this to the user before implementation starts rather than having `ux-apply` improvise it (see Implementation notes for how this ticket resolves that).
2. **`TransactionSearchComponent`'s template changes shape, its class mostly doesn't.** It currently renders as a full `ion-page` (its own `ion-header` with a back arrow + "Search Transactions" title, since it was a screen you navigated to). As an embedded child of the wrapper, it needs to lose that page chrome - keep just the filter-chip row and the two modals (account/category selectors), condensed per Option 1's tightened style. Its `seedFilters(filters)` method becomes a proper `@Input() initialFilters` (ordinary Angular data-binding now that it's a template child, not something a router-outlet's `(activate)` handler calls imperatively); `filtersApplied` stays as the `@Output` the wrapper listens to. The `cancelled` output and its "back arrow" go away entirely - there's no longer a "screen" to cancel out of, it's just inline controls on the page.
3. **Filter row**: date range, accounts, category, DR/CR - condensed into the single-row chip style already used successfully elsewhere in this app (see `transaction-list`'s original pre-split filter row, and the mockup's `Apr 1–Mar 31 ▾` / `3 accounts ▾` / `Category ▾` / `DR/CR ▾` chips). No `Apply` button - filters take effect via the **existing** header refresh icon (`refreshWithAnimation()` → `refreshTransactions()` → `loadTransactions()`), which already exists in the real code today and doesn't need to change. **Correction to the mockup**: the mockup's header shows a hamburger/filter-lines icon where the real header's refresh icon should stay - that icon was drawn for the "separate route" version of this option; there's no route to link to anymore, so `ux-apply` should keep the real header's existing refresh icon exactly as-is, not add a new one.
4. **Account/category selector modals**: reuse the real, already-built modals from `transaction-search.component.html` (grouped-by-type account modal with `isAccountGroupExpanded`/`toggleAccountGroup`, already-existing category modal with search) - unchanged, just now rendered from a component that's an embedded child instead of a routed page. `transaction-search`'s honest finding about type-grouping not separating the 33 test accounts (see Option 2 above) still applies here - keep the alphabetical-sort-plus-search framing, don't claim grouping alone solves it.
5. **Search bar** (new visual treatment, on `transaction-list`, unchanged by whichever composition wins): replace the current `ion-searchbar` (default grey pill, generic magnifier, bare `ion-checkbox` regex toggle) with a flat underline field - thin-stroke leading magnifier icon (matching the direction's icon weight), muted placeholder text, `1px solid var(--app-divider-subtle)` for the underline (idle) - and restyle the regex toggle as a small labeled switch (a two-state pill with a sliding dot, `--app-divider` track / `--ion-color-primary` when on) with an adjacent "Regex" label, replacing the bare `ion-checkbox` + separate `.regex-label` span that exist today.
6. **Error state** (new - `ux-apply` should check whether `transaction-list`'s existing `hasError`/`retryLoadTransactions()` already covers this before adding anything, since folding the filters onto the same page doesn't change how transactions are fetched): reuse the existing error-state markup/logic as-is if so.
7. **Everything else** (summary row, transaction rows, category pills, batch-categorize toolbar, empty states) - unchanged from the current real `transaction-list.component.html`, since none of that is affected by this composition change.

## Implementation notes

Grounded against the real, already-split `transaction-search`/`transaction-list` components (JIRA_14) before touching anything. Real findings:

1. **`TransactionsShellComponent` deleted, `/tabs/transactions/search` route deleted.** `tabs.routes.ts`'s `transactions` entry is a single leaf route again, now loading a new `TransactionsPageComponent` (`finance-manager-ui/src/app/transactions-page/`) instead of `TransactionListComponent` directly.
2. **Composition is Angular content projection, not two top-level template siblings.** The original plan (`<app-transaction-search>` then `<app-transaction-list>` as flat siblings in the wrapper) doesn't actually place the filter row where the mockup shows it: `transaction-list` owns the page's `ion-header` (title, row count, refresh icon), and the mockup puts the filter row *below* that header, above the summary/search-bar/rows. Two top-level siblings would put the filter row *above* the whole page instead. Fixed by adding an `<ng-content>` slot inside `transaction-list.component.html`'s `ion-content` (see finding 3 for why it has to be inside, not between header and content), and having the wrapper project `<app-transaction-search>` into it: `<app-transaction-list #list><app-transaction-search (filtersApplied)="list.applyFilters($event)"></app-transaction-search></app-transaction-list>`. The two components stay genuinely separate - `transaction-list` just reserves a slot without knowing what's projected into it - and the wrapper still wires them with a plain template reference + `@Output`, matching the spirit of "plain `@Input`/`@Output`" even though the exact shape (content projection vs. flat siblings) differs from the original text.
3. **Live-testing-only layout bug**: an early version placed `<ng-content>` between `<ion-header>` and `<ion-content [fullscreen]="true">` (normal document flow). Live in the browser this rendered the filter row and the search bar/regex toggle overlapping at the same vertical position - invisible to `ng build`/`ng test`. Cause: `ion-content[fullscreen]="true"` positions itself to slide under a translucent header using an offset computed from the header's own height only; it doesn't account for an extra sibling injected between header and content, so that sibling's height is ignored in the offset math and its content visually collides with `ion-content`'s. Fixed by moving `<ng-content>` to be the *first child inside* `<ion-content>` instead of a sibling - confirmed correct via `claude-in-chrome` afterward (filter row now renders cleanly below the title bar, above the summary row).
4. **No Apply button - the exact trigger for "filters take effect without one" was decided during implementation.** The spec named the existing header refresh icon; in practice, emitting on every account/category checkbox click would fire a transaction refetch per click, which is worse UX than any button. Chosen behavior: `transaction-search` emits `filtersApplied` immediately on a date change or DR/CR change, and once (not per-checkbox) when the account or category modal closes, if a selection actually changed - verified live via `read_network_requests`: changing DR/CR to "Credit" fired exactly one `GET /transaction/v1/fetch_all?...&debit_credit_indicator=CR` request.
5. **`TransactionSearchComponent`'s `seedFilters(filters)` became `@Input() initialFilters`, read in `ngOnInit`** (Angular sets a statically-bound `@Input` before `ngOnInit` runs, so no `ngOnChanges` was needed). The `cancelled` output, back-arrow button, and top-level `ion-header`/`ion-content`/Apply button were all removed from its template - it's just the filter-chip row plus the two selector modals now.
6. **Real, deliberately-left gap**: landing on `/tabs/transactions` via `account-list`'s row-click drill-in (`?userAccountId=<id>`) sets `transaction-list`'s own `selectedAccountIds`/loads transactions, but doesn't seed `transaction-search`'s visible "Accounts" chip (it has no `initialFilters` wired from that path). Under JIRA_14 this was invisible since the filter screen was hidden until you navigated to it; now that the chip row is always on-screen, this is a visible (if minor) inconsistency - the account IS applied and transactions load, the chip just still reads "Select accounts" until you open and re-confirm it. Not fixed here: doing so cleanly would mean `TransactionListComponent` notifying its parent of a query-param-driven filter change, which is a real design decision (a new `@Output`, or a shared source of truth) beyond this ticket's scope - noted rather than improvised.
7. **Search bar revamp**: `transaction-list`'s `ion-searchbar` restyled via CSS custom properties (`--border-radius: 0`, `--background: transparent`, flat `border-bottom`, brightening to `--ion-color-primary` on focus) rather than swapped for a hand-rolled `<input>`, since Ionic's searchbar already provides the debounce/cancel-button behavior the app relies on and its built-in icon is already a thin-stroke "outline" icon consistent with the rest of the app's iconset. The bare `ion-checkbox` regex toggle was replaced with Ionic's own `ion-toggle` (a real labeled switch component, not a hand-rolled one) plus an adjacent "Regex" label - confirmed live: track fills with the primary color and the handle slides right when checked.
8. **Error state**: `transaction-list`'s existing `hasError`/`retryLoadTransactions()` (from `ux/UX_transaction-list.md`) already covers this composition unchanged - nothing to add, matching point 6's suggestion to check first.
9. **Live-testing-only bug, found after this spec was first marked Implemented**: the "Regex" label rendered with its leading "R" invisible, at every viewport width tested, with or without the searchbar focused. Cause: the `ion-toggle` host had `width: 20px; height: 34px` and `--handle-width`/`--handle-height` set directly on it to shrink it, but Ionic's shadow-DOM track renders at its own fixed default size (~51x31) regardless of the host's declared width/height or handle custom properties - those only resize the host's own layout box, not what actually paints inside it. The unshrunk track visually overflowed ~17px past its host box and painted over the first few pixels of the adjacent "Regex" label. Fixed by using `transform: scale(0.65)` with `transform-origin: left center` instead of `width`/`height`/`--handle-*` - a transform shrinks the actual painted content (so nothing overflows), and because it doesn't change the element's layout box, the label after it is still sized against the toggle's original (larger, unscaled) footprint, so there's always genuine room. Confirmed fixed live via `claude-in-chrome`, both at rest and with the searchbar focused (cancel button showing).
10. **Verification**: `ng build --configuration development` clean (only pre-existing unused-import warnings). Full suite `ng test --browsers=ChromeHeadless --watch=false` - 124/124 passing (replaced `transactions-shell.component.spec.ts` with `transactions-page.component.spec.ts`; reworked `transaction-search.component.spec.ts`'s seed/apply/cancel tests into `initialFilters`/emit-on-change tests). Live-verified end-to-end via `claude-in-chrome` against the running `local-run` stack: opened `/tabs/transactions`, selected the real `hdfc` account via the modal (chip updated, list refetched), changed DR/CR to Credit (confirmed via network inspection that exactly one real HTTP request fired with `debit_credit_indicator=CR`), typed into the revamped search bar and toggled the new `ion-toggle` regex switch (both rendered and behaved correctly), and deselected the account to confirm the updated "No accounts selected" copy (no dead link) renders correctly with the filter row still visible above it.
