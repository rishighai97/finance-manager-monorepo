# UX_graphs: Graphs (new page)

**Status**: Implemented <!-- Draft -> Options Presented -> Selected -> Ready for Dev -> Implemented -->
**Created**: 2026-09-19
**Last updated**: 2026-09-19
**Direction**: [ux/UX_DIRECTION.md](UX_DIRECTION.md) - "Calm Ledger", Ready for Dev

## Page
`graphs` (new - `finance-manager-ui/src/app/graphs/`, to be added as its own bottom tab per [jira/JIRA_23.md](../jira/JIRA_23.md)). A graph-type dropdown drives which of four graph types renders (Spending by category, Income vs. expense over time, Balance trend over time, Monthly spending trend); a filter button on the right opens the same Filters sheet already implemented for `transaction-search` (see [ux/UX_transaction-search.md](UX_transaction-search.md)) via the reusable filter component JIRA_23 extracts from it - this round does not redesign that sheet, only where its trigger sits on this new page.

## Options presented

Real data pulled via `db-run` against the local `finance_manager` database. The `transaction` table was empty (reset earlier this session) so 4 synthetic statements (Canara, Axis, Groww, Amex - `scripts/statements/synthetic/`) were uploaded through the running `statement-loader` to populate 15 real transactions across 4 real accounts, then 3 were categorized (`Salary Credit`&rarr;SALARY, 2&times;`Grocery Store`&rarr;FOOD) via `transaction_user_category` - the rest are genuinely uncategorized, which the mockup shows honestly rather than force-categorizing content that doesn't fit the 5 real categories (SALARY/FOOD/LUNCH/DINNER/SNACKS).

**Real finding while building this**: `closing_balance` is only populated on the two bank-savings statement formats (Canara, Axis) - Groww's mutual-fund rows and Amex's credit-card rows never carry one (confirmed via `SELECT title, closing_balance FROM transaction`). **Balance trend over time therefore only means something for a single balance-bearing account at a time** - both options scope that graph type to "exactly one balance-bearing account selected" and show a guidance state otherwise, rather than summing or charting balances across heterogeneous accounts (which would be meaningless - different accounts, no shared running total).

### Option 1 - Spare
- **Artifact**: [Graphs Page Options](https://claude.ai/artifact/1RH4fKvTWzFGDRhu632def) (left column)
- **Layout**: title, then the dropdown + filter-icon row, then the chart fills essentially the whole remaining screen - no other chrome. Closest to Calm Ledger's "quiet, considered" brief; the chart has to carry all context on its own (e.g. the donut's center label carries the total).
- **States covered**: happy (all 4 real graph types, live-switchable via the dropdown in the artifact), loading (skeleton donut/bars under the controls row), empty ("No transactions match the current filters" with an "Adjust filters" link), error ("Couldn't load transactions" + Retry) - see the artifact's states strip under the frame.

### Option 2 - Context strip
- **Artifact**: [Graphs Page Options](https://claude.ai/artifact/1RH4fKvTWzFGDRhu632def) (right column)
- **Layout**: same controls row, but adds one compact mono-figure stat row between the controls and the chart - the 1-3 numbers that change meaning with the selected graph type (e.g. total spend + top category for the category view; income/expense/net for the income-vs-expense view), so the headline number reads before looking at the chart at all.
- **States covered**: same four as Option 1, plus the stat strip itself updates live with the dropdown in the artifact (also skeletons during loading, per the states strip).

Both options reuse the real, already-implemented Filters sheet (date range, accounts, categories, DR/CR, Apply/Clear) as a static preview - tapping the filter icon in either mockup opens it, matching the real component JIRA_23 extracts for reuse. Neither option redesigns that sheet.

## Selected option
**Option 1 - Spare**, confirmed by the user, with one addition: hover interactivity (already prototyped on the donut/bars/points in the artifact) is a hard requirement, not just a nice-to-have of the mockup - every mark must expose its exact value on hover, not only via the direct labels already shown for some chart types.

## Implementation detail

Grounded against the real `finance-manager-ui/src/app/transaction-list/` header/filter-button pattern (the closest existing precedent) and `ux/UX_DIRECTION.md`'s Calm Ledger tokens.

1. **Page shell**: new `finance-manager-ui/src/app/graphs/graphs.component.{ts,html,scss}`, added as a new leaf route/tab (`tabs.routes.ts`'s `graphs` entry, `tabs.page.html`'s new `ion-tab-button` between Transactions and Categories - matches the artifact's tab order). Header uses the same `ion-header`/`ion-toolbar`/`ion-title.cl-headline` pattern as `transaction-list.component.html`, title text "Graphs", no `ion-buttons`/meta-count on the right (unlike Transactions' row-count) since there's nothing analogous to show there.
2. **Controls row** (below the header, inside `ion-content`): a native `<select>` (styled per the artifact - transparent background, bottom hairline `1px solid var(--app-divider-subtle)`, small chevron, `IBM Plex Sans` 13px/500) listing all four graph types in fixed order (Spending by category, Income vs. expense over time, Balance trend over time, Monthly spending trend), plus the filter button reusing the **exact existing markup/behavior** from `transaction-list.component.html`: `<button class="filter-btn" (click)="onFilterButtonClick()">` with `ion-icon name="options-outline"` and a `.filter-btn-dot` shown when `hasActiveFilters` - both now living on the shared, extracted filter component's host page instead of being copy-pasted, per JIRA_23's Requirement 1/2.
3. **Chart area**: fills the remaining `ion-content` height. Each of the four graph types is its own render function (matching the artifact's `renderCategoryDonut`/`renderIncomeExpense`/`renderMonthlySpend`/`renderBalance` split) producing inline SVG - no charting library needed for these four forms (donut, grouped bars, single-series bars, a 4-point line), so JIRA_23's approved Chart.js dependency should only be added if `ux-apply` finds a concrete reason inline SVG doesn't scale (e.g. many-month line trends with dozens of points) - note that reasoning here if so, don't add the dependency by default.
4. **Colors**: credit/debit reuse the app's existing semantic tokens exactly (`--ion-color-success` / `--ion-color-danger`, i.e. the sage/clay pair) for Income vs. expense and the single-series Monthly spending trend (debit-only, so clay throughout); the Balance trend line uses `--ion-color-primary` (the accent rust), consistent with it being the app's one "emphasis" data line rather than a debit/credit event. The category donut's per-category hues are the `dataviz` skill's validated default categorical set used **as literal hex, not re-themed** (`#2a78d6`, `#eb6834`, `#1baf7a`, `#eda100`, `#e87ba4`, capped at 5 named categories before folding into "Other"); "Uncategorized"/"Other" always renders last in `--app-color-muted` regardless of how many named categories are present. If a future pass wants these retinted to Calm Ledger's warmer register, re-run `scripts/validate_palette.js` on the candidates first - every hand-retinted attempt made during this exploration failed the chroma-floor/CVD checks (see Changelog), so don't reuse those specific attempts.
5. **Hover interactivity (the addition from this round)**: every mark gets a real mouse-driven tooltip, not just a browser-default `<title>` - reuse the artifact's `showTip`/`hideTip` pattern (a single absolutely-positioned tooltip div, shown on `mousemove` over each mark, hidden on `mouseleave`), styled `--ion-text-color` background / `--ion-background-color` text, `IBM Plex Sans` 11px. Donut slices show `<amount> · <category> (<pct>%)`; income/expense and monthly-spend bars show `<amount> · <Income|Expense|month>`; balance-trend points show `<amount> · <date>`. This is required on every mark in every graph type, not only the ones already demoed - the artifact prototyped it on all four, so there's no new interaction pattern to invent, just wire the same one consistently.
6. **Filter application**: applying filters (via the shared component's existing `filtersApplied` output) or changing the dropdown re-fetches via the existing `TransactionService`/`/transaction/v1/fetch_all` (same call `transaction-list` already makes) and recomputes whichever chart is active client-side - no new backend calls beyond that one endpoint.
7. **Balance trend's account constraint**: when the active account filter selects anything other than exactly one account that has at least one non-null `closing_balance` row, render the guidance state described below instead of a chart (this is a real, load-bearing state, not just an edge case - most filter combinations won't satisfy it, since only bank-savings-style statements populate `closing_balance`).
8. **States**:
   - **Happy**: as demoed per graph type.
   - **Loading**: skeleton donut ring / skeleton bars under the controls row (artifact's `.skeleton-donut`/`.skeleton-bar`), matching `transaction-list`'s existing skeleton-loading convention rather than inventing a new one.
   - **Empty** (no transactions match the active filters for the selected graph type): centered message "No transactions match the current filters." plus an "Adjust filters" text link that calls the same filter-button handler - mirrors `transaction-list`'s existing "No accounts selected" -> "Select accounts" link pattern.
   - **Error** (the `/fetch_all` call fails): centered "Couldn't load transactions." + a Retry action - reuse `transaction-list`'s existing `hasError`/`retryLoadTransactions()` mechanism if the shared data-fetch is factored so this component can call it, rather than re-implementing error handling from scratch.
   - **Balance-trend guidance state** (not a generic empty/error - a fifth, graph-type-specific state): shown only when "Balance trend over time" is selected and the account filter doesn't resolve to exactly one balance-bearing account. Copy: "Balance trend needs exactly one account with balance history selected." plus the same "Adjust filters" link.

## Implementation notes

Grounded against the real `finance-manager-ui/src/app/transaction-list/`, `transaction-search/` (now extracted), and `tabs/` before touching anything.

1. **Filter extraction was a plain move + rename, no behavior change.** `transaction-search/` moved to `shared/transaction-filter/transaction-filter.component.{ts,html,scss,spec.ts}` (`git mv`, preserving history), `TransactionSearchComponent` -> `TransactionFilterComponent`, `app-transaction-search` -> `app-transaction-filter`. `TransactionFilters` (the interface) kept its name and shape - it was already generic. `transaction-list.component.ts`'s import path and `transactions-page.component.ts/html`'s wiring were updated to match; nothing about the filter's actual behavior changed.
2. **No `@Output`/coordinator needed on the Graphs page**, unlike `transaction-list`/`transactions-page`'s two-component forwarding (`openFilters` -> `openFilterModal()`). `GraphsComponent` hosts both the filter button and `<app-transaction-filter>` directly in one template, so a template reference variable (`#filterComp`) lets the button - and the "Adjust filters" links inside the empty/guidance states - call `filterComp.openFilterModal()` straight from the template. Simpler than transaction-list's pattern because there's no cross-component projection here.
3. **Default account selection on first load (real implementation-time decision, not specified by the spec)**: unlike `transaction-list` (which seeds one account from a `?userAccountId=` query param), Graphs has no equivalent entry point, so it defaults to *every* account the user has once `groupedUserAccounts$` first emits - giving the full picture on first visit rather than an empty chart. Re-evaluate if this turns out to be the wrong default for accounts with very different statement histories (e.g. a newly linked account with no data yet).
4. **Multi-category transactions double-count in the category donut, by design.** A transaction tagged under N categories contributes its full amount to each of the N slices (matching how the category pills already show it under every assigned category), so `categoryTotal` can exceed true total spend when multi-tagged transactions exist. Covered by a dedicated test (`graphs.component.spec.ts`).
5. **Category color validation, not solved, deliberately deferred**: per the spec's own note, the category donut uses the `dataviz` skill's validated default hues (`#2a78d6`, `#eb6834`, `#1baf7a`, `#eda100`, `#e87ba4`) as literal hex rather than a Calm-Ledger-retinted set - every retint attempt during `ux-explore` failed the skill's colorblind-safety validator. Left as a named follow-up in the component's own code comment (`CATEGORY_COLORS`), not silently worked around.
6. **`Transaction.closing_balance` is typed `number` in `src/model/transaction.ts` but is genuinely `null` at runtime** for statement formats with no running balance (confirmed against real Groww/Amex data - see `ux/UX_graphs.md`'s Options section). `GraphsComponent` checks `!== null && !== undefined` against it anyway (TypeScript allows this without error even though the declared type says otherwise) rather than "fixing" the model's type, since that's a `src/model/*.ts` contract change beyond this UI-only ticket's scope - noted here rather than touched.
7. **Balance-trend guidance state is the one state that's genuinely hard to avoid hitting**: since only 2 of the app's 7 real local accounts (Canara, Axis) carry `closing_balance`, selecting "Balance trend over time" with the page's own default (all accounts selected) always shows the guidance state until the user filters down to exactly one of those two - this is correct/intended per the spec, not a bug, but worth calling out since it's the state a first-time visitor to this graph type will actually see most often.
8. **Verification**: `ng build --configuration development` clean (only pre-existing unused-import warnings, none from this change). Full suite `ng test --browsers=ChromeHeadless --watch=false` - **138/138 passing** (11 new tests in `graphs.component.spec.ts` covering default account selection, category aggregation - including the multi-category double-count and the >5-categories-fold-into-Other rule - month grouping, the balance-trend single-account constraint, and error/retry; all pre-existing `transaction-list`/`transactions-page`/`transaction-filter` specs still pass unchanged after the rename).
9. **Live browser check (follow-up pass, `claude-in-chrome` connected) found three real bugs invisible to `ng build`/`ng test` - the user reported the first two directly ("filter icon is not visible", "Graph is too huge"):**
   - **Header-overlap bug**: `ion-content[fullscreen]`'s automatic header-height offset wasn't applying (`--padding-top` computed to `0`), so the controls row (dropdown + filter button) rendered 44px too high, hidden under the header - only a ~4px sliver of the filter button's border poked out. This is the same class of bug `transaction-list` hit before (see `ux/UX_transaction-search.md`'s Implementation notes point 3/12); same fix applied - dropped `[fullscreen]`/`[translucent]` entirely, since this app's header is already fully opaque and doesn't need the offset mechanism. Confirmed fixed live: the dropdown and filter icon both render clearly below the header now.
   - **Chart ballooning bug**: the category donut rendered at ~608x608px, spilling well past the viewport, on a real desktop browser window. Root cause, found via `getComputedStyle`/`getBoundingClientRect` on the live page: `.chart-svg-wrap` had `flex:1; max-height:340px` (no explicit `height`), and `svg.chart` had `height:100%` - a percentage height only resolves against a parent with a *definite* height, which a flex item constrained only by `max-height` does not have, so `height:100%` fell back to matching the SVG's (large, definite) width instead of the intended cap. Fixed by giving `.chart-svg-wrap` an explicit `height: 280px` instead of `flex`/`max-height`, which makes the child's percentage height actually resolve. Confirmed fixed live across all four graph types (roughly 215px-tall charts now, well-proportioned).
   - **Stale tooltip bug** (found during this same live pass, not user-reported): switching graph types didn't clear the previous chart's hover tooltip, leaving e.g. the category donut's tooltip text floating over the newly-selected income/expense bars. Fixed by calling `hideTooltip()` in `onGraphTypeChange()`. Confirmed fixed live.
   - All three fixes verified against real, richer pre-existing account data in the running app (not the synthetic `ux-explore` dataset) - the "hdfc" account's actual transaction/balance history, spanning several years, rendered correctly at a sane size for all four graph types after the fixes, including a many-point balance trend line.
   - Full test suite re-run after these fixes: **138/138 still passing** (11/11 in `graphs.component.spec.ts`).
