# Skills catalog

Every Claude Code skill defined in this repo (`.claude/skills/<name>/SKILL.md`), with its purpose and when it's used. This page is the index referenced from the "Skills" section of the root `CLAUDE.md` - **whenever a skill is added, renamed, or removed, update this table in the same change** (see `CLAUDE.md`'s "Skills" section for the enforcement of that rule).

| Skill | Purpose | When it's used |
|---|---|---|
| [`jira-create`](../.claude/skills/jira-create/SKILL.md) | Capture a one-line requirement as a `jira/JIRA_<ID>.md` spec file and iteratively refine it with the user until it's explicitly marked Ready for Dev. | Any new feature/bug/requirement for finance-manager, before implementation starts. |
| [`local-setup`](../.claude/skills/local-setup/SKILL.md) | Verify/repair local prerequisites: Java toolchain reachability for the 3 Gradle services, a Python venv with `statement-loader`'s dependencies, `finance-manager-ui`'s npm dependencies, and a local Postgres with the `finance_manager` database created. | Before `local-run` on a fresh checkout or new machine, or whenever a prerequisite looks broken. Doesn't touch application data, and doesn't install missing system tools itself (see `local-install`). |
| [`local-install`](../.claude/skills/local-install/SKILL.md) | Install/upgrade Java, Node/npm, the Ionic CLI, and Docker via Homebrew (macOS) or apt (Debian/Ubuntu Linux), defaulting to the version this project needs but accepting a `--version` override. Refuses to run on Windows. Interactive - installs then verifies each tool actually works before ticking it off a checklist, looping with the user if a manual step (e.g. opening Docker Desktop) remains. | When `local-setup` reports one of these tools missing, or whenever asked to install/upgrade the local toolchain. Actually installs system software - a deliberate, user-initiated action, never a silent side effect of `local-run`. |
| [`db-run`](../.claude/skills/db-run/SKILL.md) | General-purpose SQL runner for the `dbscripts/` module: executes an ordered manifest, a single `.sql` file, or an inline SQL string against the local `finance_manager` Postgres via the real `psql` CLI (no Python/psycopg2). | Whenever running one of `dbscripts/`'s versioned SQL files, or an ad-hoc query, against the local database. `db-setup` delegates to it for the full reset flow. |
| [`db-setup`](../.claude/skills/db-setup/SKILL.md) | Destructively drop and recreate every table in the local `finance_manager` database, then load sample data (accounts, account types/icons, a demo user, categories) - by running `dbscripts/script/{teardown,setup}.list` via `db-run`. | Resetting local data to a known-good state, or automatically by `local-run` on a first-time empty database. **Destructive** - never run against data worth keeping. |
| [`local-run`](../.claude/skills/local-run/SKILL.md) | Root-level orchestrator: runs `local-setup` and (if needed) `db-setup` automatically, then starts Postgres-dependent services + the UI so the app is reachable on `localhost`. | Whenever the user wants to run/start the whole local stack and view the app on `localhost` with minimal manual steps. |
| [`scenario-discovery`](../.claude/skills/scenario-discovery/SKILL.md) | Reads the backend services' actual API surface and produces/updates a catalog of business-level test scenarios (not code) in `test-automation/README.md`. | Finding/documenting what user scenarios exist to test, refreshing the catalog after an endpoint changes, or before `bdd-test-generate` on an uncatalogued scenario. |
| [`bdd-test-generate`](../.claude/skills/bdd-test-generate/SKILL.md) | Turns one catalog scenario into a runnable Cucumber BDD test (`RestTemplate` backend test), runs it against a live stack, and flips the catalog row to `Implemented`. | Adding/generating a test for a specific scenario in `test-automation`, or implementing the next `Planned` catalog row. |
| [`unit-test-generate`](../.claude/skills/unit-test-generate/SKILL.md) | Writes real unit tests (JUnit 5 + Mockito / pytest / Jasmine-Karma per module) in one of two modes: existing-feature (characterization tests, no behavior change) or new-feature (TDD - tests first from a ticket's acceptance criteria, then implementation). Enforces a 60% coverage floor per module and the `@Nested`/`@DisplayName` Java test-naming convention. | Backfilling unit test coverage on existing code, or implementing any new ticket test-first (the default going forward). |
| [`diagram-maintain`](../.claude/skills/diagram-maintain/SKILL.md) | Creates and updates `architecture-docs/`'s Mermaid-based architecture diagrams (HLD, sequence, ER) so they stay accurate as the codebase changes. | Proactively, whenever a code change affects architecture (new/changed endpoint, inter-service call, DB table, or UI-visible flow) - not only when explicitly asked for a diagram update. |

## Conventions these skills share

- Each skill's `SKILL.md` is both its documentation and the thing Claude Code reads to decide when to invoke it (via its frontmatter `description`) - there's no separate README per skill.
- `local-setup`, `local-install`, `db-run`, `db-setup`, and `local-run` each have a backing shell script alongside their `SKILL.md` (`check-and-setup.sh`, `install.sh`, `run-sql.sh`, `reset-db.sh`, `start-all.sh`/`stop-all.sh`) that does the actual work; the `SKILL.md` explains what the script does and how to interpret its output, rather than duplicating its logic in prose.
- All of them resolve the repo root from their own script location (`$(dirname "${BASH_SOURCE[0]}")/../../..`), so they work from any checkout path - unlike the older `scripts/local_startup/*.sh`, which hardcode a pre-monorepo path.
- `local-setup`/`db-setup`/`local-run` are Mac/Linux-only by inheritance of the existing local dev scripts; `local-install` additionally refuses to run on Windows explicitly (rather than just being undocumented there), since it's the one skill that would otherwise attempt OS-specific package-manager commands.
- Local defaults match every backend service's `application-local.properties`: Postgres on `localhost:5432`, database `finance_manager`, user `postgres`, password `admin`.
- `scenario-discovery`, `bdd-test-generate`, `unit-test-generate`, and `diagram-maintain` are the exception to the "backing script" pattern above - they're judgment/code-generation skills Claude executes directly (reading source, writing test/step-definition files, updating a catalog or coverage config, or rewriting a Mermaid diagram), not deterministic scripts. Their output lives in `test-automation/`, each service/UI module's own `src/test`/`spec` tree, or `architecture-docs/` - not in `.claude/skills/`.
- `diagram-maintain` is the one skill meant to trigger proactively from its `SKILL.md` description alone (mid-session, off an architecture-affecting code change) rather than only when the user names it - see that file's frontmatter for the exact trigger conditions.
