# JIRA_12: `ux-explore` and `ux-apply` skills for a finance-manager-ui UX overhaul

**Status**: In Progress <!-- Draft -> In Refinement -> Ready for Dev -> In Progress -> Done -->
**Created**: 2026-09-11
**Last updated**: 2026-09-11 (round 3)

## One-liner
Create skills for a UX overhaul: `ux-explore` to generate comparable UX mockup options for existing finance-manager-ui pages so the user can decide on a direction, and `ux-apply` to implement the approved direction into the real UI.

## Summary
finance-manager-ui's existing pages (account-list, transaction-list, category-list, statement-uploader, auth, tabs) are getting a UX overhaul. Rather than redesigning directly in code, this introduces a two-phase, spec-driven workflow mirroring `jira-create`'s Draft -> Ready for Dev gate: `ux-explore` produces clickable HTML mockups (via the `design` skill's canvas) - first a handful of app-wide style directions on representative screens, then per-page layout variants within the chosen direction - and records decisions in `ux/` spec files; `ux-apply` reads an approved per-page spec and implements it into the real Angular/Ionic components, one page at a time.

## Scope

### In scope
- New skill `ux-explore`:
  - Round 1 (app-wide direction, run once or whenever revisiting the whole app's look): generate ~3 distinct style-direction mockups (typography, color palette, spacing/density, navigation pattern) applied to 1-2 representative screens, as clickable HTML artifacts with fake data via the `design` skill. User picks one direction (or asks for further iteration).
  - Chosen direction recorded in `ux/UX_DIRECTION.md` (shared style contract: color tokens, type scale, spacing rules, component style, nav pattern).
  - Round 2 (per page): for each existing page, generate 2-3 layout variants within the approved direction as further mockup artifacts, populated with real data pulled from the local Postgres via the `db-run` skill (not synthetic fake data) - requires a locally running/seeded DB (see `db-setup`) as a dependency of this round. Variants must also cover that page's empty, error, and loading states, not just the happy path. Each page gets its own `ux/UX_<page>.md` spec file, going through the same Draft -> Options Presented -> Selected -> Ready for Dev gate as `jira-create`, recording the chosen variant (including its empty/error/loading treatments), artifact link, and enough concrete detail (layout, key components, interaction notes) to implement from.
- New skill `ux-apply`:
  - Takes one `ux/UX_<page>.md` marked Ready for Dev and implements it into the real Angular/Ionic components for that page in `finance-manager-ui`, including the happy-path, empty, error, and loading states described in the spec.
  - Reuses Ionic's component library rather than inventing new primitives per page.
  - Leaves the existing `src/service/*.service.ts` HTTP client layer untouched - UI/UX only, no API contract changes.
  - Edits directly on the current branch (no automatic branch/PR-per-page) - the user controls branching/committing.
  - Runs one page at a time, producing a small reviewable diff per page (not one repo-wide rewrite).
- `docs/SKILLS.md` updated with both new skills (per `CLAUDE.md`'s rule that skill additions must keep that catalog in sync).
- Clean-slate design: no existing brand/design system constraints to preserve.
- Pages covered: account-list, transaction-list, category-list, statement-uploader, auth, tabs - each including its empty, error, and loading states.
- New skill `ux-proof-capture` (scoped to this ticket only, not a general-purpose skill): generates a sample statement file for every `statement-loader` reader (extends `scripts/generate_dummy_statement_fixtures.py` with an `--out-dir` option, writing to `scripts/statements/synthetic/`), then drives a full login/upload/categorize walkthrough on the HDFC RISHI and AXIS RISHI demo accounts via `claude-in-chrome`, captured as an animated GIF. Run once before `ux-apply` changes land (the "before" baseline) and once after (the "after" comparison) as visual proof of the overhaul - see `.claude/skills/ux-proof-capture/SKILL.md`.

### Out of scope
- Actually running the exploration/decision process itself (picking the app-wide direction, picking per-page variants) - that happens after this ticket, using the skills once built.
- Backend/API changes of any kind.
- finance-manager-ui's non-page chrome not listed above, unless it's part of the shared direction contract (e.g. tabs nav styling) established in `ux/UX_DIRECTION.md`.
- Capacitor/iOS-specific UI concerns beyond what Ionic's web components already handle.

- Design decisions made while building these:
  - `ux/` mirrors `jira/`'s Draft-refine-Ready-for-Dev discipline but with its own 4-state lifecycle (`Draft -> Options Presented -> Selected -> Ready for Dev`) rather than reusing `jira/TEMPLATE.md` directly - a UX option-comparison spec doesn't fit a requirements/acceptance-criteria shape.
  - `ux-apply` maps `UX_DIRECTION.md`'s color tokens onto Ionic's existing `--ion-color-*` custom properties in `finance-manager-ui/src/theme/variables.scss` rather than inventing new ones, and applies the shared direction tokens globally only on its first run per direction version (checked against `variables.scss`'s current values, not re-applied blindly every page).
  - `ux-apply` explicitly excludes `finance-manager-ui/src/app/{tab2,tab3,explore-container,logout}` - unrelated Ionic-starter-template leftovers not in JIRA_12's six-page scope.

This requires live user UX decisions this ticket doesn't make unilaterally - see the three unchecked Acceptance criteria above.

  - [`category-list`](../ux/UX_category-list.md) - Option A (inline text-link actions); preserves the real staged-change model (rename/delete queue until "Save Changes").
  - [`statement-uploader`](../ux/UX_statement-uploader.md) - Option B (unified list); a real behavior change (merges the today-separate queue/results arrays into one status-tracked list), not just a restyle.
  - [`auth`](../ux/UX_auth.md) - Option B (no card, full-bleed); removes a redundant duplicate heading and the screen's `ion-header`.
  - [`tabs`](../ux/UX_tabs.md) - Option B (remove the side menu); it duplicated the tab bar exactly and had no discoverable way to open it in the real app (no `menuController` call anywhere).

- **Update 3**: ran `ux-apply` for the first time, against `account-list` (Option C). Real code changed: `account-list.component.{html,ts,scss}`, plus the app-wide Calm Ledger tokens applied globally for the first time (`finance-manager-ui/src/theme/variables.scss`, `src/global.scss`, `src/index.html` - including turning off Ionic's auto-dark-mode palette, since Calm Ledger has no designed dark variant). Two real findings, recorded in `ux/UX_account-list.md`'s new Implementation notes section: (1) the collapsible-sections feature turned out to already exist as dead code (`isExpanded`/`toggleLevel1Group()` were unused leftovers) - implementing it was mostly *reviving* that, not writing it fresh; (2) the new error state is real, correct, and unit-tested, but currently **unreachable** in the live app because `UserAccountService` swallows its own HTTP errors and never propagates them to the `BehaviorSubject` the component subscribes to - fixing that would touch a `src/service/*.service.ts` file, out of `ux-apply`'s scope, so it's flagged rather than fixed. Also used `unit-test-generate` (existing-feature mode) to add 8 characterization tests for the new/revived logic (9/9 passing). `ng build` clean. **Not done this run**: a live browser check - the `claude-in-chrome` extension wasn't connected this session; noted explicitly rather than claimed. In the process, found and fixed two real gaps in `ux-apply`/`ux/TEMPLATE.md` themselves (a stale `npm run lint` reference - no lint target exists in this project; and no terminal "Implemented" status or place to record post-build findings) - see `docs/SKILLS.md`'s Conventions section and the skill/template files directly. No new skill was warranted for this; a future candidate if the pattern repeats is a lightweight "ux-verify" skill that automates the live-browser sanity check per state, but that's speculative until the live-check gap actually recurs.
- **Update 4**: the user actually looked at the running app and reported the color theme wasn't applying - they were right. Root cause: `variables.scss` was wired into `angular.json`'s `styles` array *before* `global.scss`, whose own Ionic `core.css` import then silently redefined the same `--ion-color-*` variables afterward in the final bundle - same specificity, last rule in the concatenated CSS wins, so Ionic's defaults beat Calm Ledger's tokens everywhere, with no build error and no failing test. Fixed by importing `variables.scss` from *inside* `global.scss`, after Ionic's own imports (the standard Ionic pattern), and reverting the `angular.json` change. Confirmed both in the compiled CSS and via a live `claude-in-chrome` check once the extension reconnected. **This is a systemic fix, not just an `account-list` one** - every subsequent page's `ux-apply` run benefits from it, and `.claude/skills/ux-apply/SKILL.md`'s Step 2 now calls out the gotcha explicitly so a future run (or a fresh session with no memory of this) doesn't repeat it. Worth noting for the general pattern: build/lint/unit-test passing is not the same as the change actually working - this one only surfaced because a human looked at the real running app.
- **Update 5**: ran `ux-apply` for `transaction-list` (Option A). Real code changed: `transaction-list.component.{html,ts,scss}` only - the app-wide color-wiring fix from Update 4 needed no rework, verified still correctly in place before touching this page. Two real findings, recorded in `ux/UX_transaction-list.md`'s new Implementation notes: (1) the spec's Implementation detail wrongly assumed the real screen groups transactions under date-section headers the way `account-list` groups accounts by type - the real template is a flat list with each row showing its own date inline, and there's no grouping mechanism to preserve; built what's actually there instead of inventing a date-grouping feature nobody asked for. (2) the real "batch categorize" toolbar (bulk-apply/delete/revert a category across filtered rows) was missing from both the mockup and the Implementation detail entirely - restyled it in place rather than dropping it, and flagged the spec gap for a future `ux-explore` round. Unlike `account-list`, this page's new error state is **genuinely reachable**: `TransactionService.fetchAllTransactions()` returns the raw HTTP observable with no internal error-swallowing (contrast `UserAccountService` in Update 3), so `hasError`/`retryLoadTransactions()` aren't just defensive code. Added 6 new characterization tests via `unit-test-generate` (error/retry, collapsible-group toggle, account-name lookup) - full suite 94/94 passing, `ng build` clean. Live-checked via `claude-in-chrome` against the running `local-run` stack: loaded 119 real transactions, confirmed the batch-categorize row, per-row account tags, plain-text category pills, and the collapsible "Select Accounts" modal group all render correctly in Calm Ledger's tokens. `transaction-list` marked Implemented.
- **Update 6**: ran `ux-apply` for `category-list` (Option A). Real code changed: `category-list.component.{html,ts,scss}` only. Grounded against the real component first, which confirmed most of the spec directly: the staged-change model (`toggleDelete`/`renameCategory`/`cancelRename`/`checkPendingChanges`), the native `AlertController` rename prompt, and the existing search/typeahead all mapped straight across, restyled only. Two real findings, recorded in `ux/UX_category-list.md`'s Implementation notes: (1) the spec's own usage-count idea (point 1) was dropped, not built - `CategoryService.fetchAllCategories()` and the `UserCategory` model don't carry a per-category transaction count, and adding one would mean either a new API call per row (which the spec explicitly said not to do) or a backend change to `transaction-service`, both out of `ux-apply`'s UI-only scope; the spec anticipated this exact outcome and said to drop the line rather than block, which is what happened. (2) the new error state has the same root-cause gap as `account-list`'s (`CategoryService` swallows its own HTTP errors before they reach the subject the component subscribes to) **plus an added wrinkle**: because the subscription is a one-time `ngOnInit` subscribe to a `BehaviorSubject` (not a fresh observable per retry, unlike `transaction-list`'s), RxJS semantics mean that subscription would be permanently dead after any error - so even if the swallowing were fixed, tapping "Retry" alone wouldn't be enough to recover the list without a page reload. Also removed genuinely dead code (`statusActive`/`toggleStatusActive()`) whose only UI hook was deleted along with the old `status-container` click-to-highlight wrapper. Added 3 characterization tests via `unit-test-generate` (this component had zero tests before) - full suite 97/97 passing, `ng build` clean. Live-checked via `claude-in-chrome`: confirmed Rename/Delete staged states (accent/danger left border, strikethrough, working Undo), the batch action bar (Reset All / Save Changes as plain text links), the search-miss empty state, and the Add Category modal all render correctly. `category-list` marked Implemented.
