# JIRA_14: Split transaction-list into separate search and list components

**Status**: Done <!-- Draft -> In Refinement -> Ready for Dev -> In Progress -> Done -->
**Created**: 2026-09-11
**Last updated**: 2026-09-11 (addendum - Done)

## One-liner
Separate components to have transaction search and transaction list as separate components in transaction component.

## Summary
`finance-manager-ui/src/app/transaction-list/transaction-list.component.ts` (1100+ lines) currently owns everything: the date/account/category/search filter controls, the batch-categorize toolbar, and the transaction rows themselves, all in one component with one large template. This is a pure code-structure-and-navigation refactor - split the filter/search/toolbar region into its own routed component (`transaction-search`) and keep the transaction rows in `transaction-list`, communicating via a parent container using `@Input`/`@Output`. **`transaction-search` gets its own route**, not an inline block on the same screen - the transaction list's own screen gets a trigger (exact UI TBD, likely a filter/search icon in the header) that navigates to it; applying filters there navigates back to (or updates) `transaction-list` with the new filter state. No visual/design change is in scope here beyond what's needed to add that navigation trigger; that's what JIRA_13 is for. **This ticket lands first** - JIRA_13's eventual `ux-apply` run then targets the already-separated, already-routed `transaction-search` component, landing a smaller, cleaner diff for the visual redesign.

## Scope

### In scope
- Extract only the pure filter controls (date range, account selector + modal, category selector + modal, search bar + regex toggle) out of `transaction-list.component.*` into a new standalone, routed component (`transaction-search`).
- Keep the batch-categorize toolbar (category-to-apply select, Categorize/Delete Category/Revert Categorize/Update Categories) on `transaction-list` - **corrected during implementation grounding**: it operates on `filteredTransactions`, the rows currently visible on `transaction-list`; since `transaction-search` is a separate route you navigate away to, the toolbar can't sensibly act on rows that aren't visible there. Originally scoped to move with the filters; moved back after this was caught (see Implementation notes).
- Keep the transaction rows, summary row, empty/error/loading states, and their rendering logic in `transaction-list.component.*`.
- Define how the two components communicate (e.g. `@Input`/`@Output`, a shared service, or a parent container component) - this is the main design decision for this ticket.
- Update/add unit tests for both resulting components (via `unit-test-generate`, existing-feature mode - behavior is unchanged, so this is a characterization/seam-change situation, not TDD).

### Out of scope
- Any visual/UX change to the search section - that's JIRA_13, which should build on top of whatever component structure this ticket produces (or vice versa, depending on which lands first).
- Any change to `src/service/*.service.ts` files.
- Splitting any other page's component (this is scoped to transaction-list only).

**Correction found during implementation**: `account-list.component.html` also embeds `<app-transaction-list [accountId] [groupedAccounts] (backClicked)>` inline (the "view this account's transactions" drill-in), not just the routed `/tabs/transactions` tab. That embedded usage has no way to reach a separately-routed `transaction-search` (no nested router-outlet inside the embedding). Resolved: `account-list.component.ts`'s drill-in action is changed to `router.navigate(['/tabs/transactions'], {queryParams: {userAccountId}})` instead of toggling the embedded component - `transaction-list` already reads that query param as a fallback today, so this is a small, low-risk change, and it removes the embedded-component code path entirely rather than maintaining two. This does touch `account-list.component.{html,ts}`, narrowly widening the "transaction-list only" scope line above.

## Requirements
1. New standalone, routed component `transaction-search` owns the filter controls' template, state, and handlers (date range, account/category selector modals, search bar/regex) currently in `TransactionListComponent`. Add its route under `tabs.routes.ts`.
2. `TransactionListComponent` keeps the transaction rows, summary row, and the batch-categorize toolbar (which stays here, not in `transaction-search` - see Scope correction), plus a new trigger (button/icon) that navigates to `transaction-search`'s route.
3. Applying filters in `transaction-search` returns to `transaction-list` with the new filter state applied - via the parent shell's `(activate)`-based `@Output`/`@Input` wiring (see Open questions' resolution).
4. Whatever cross-component data these controls currently share directly (e.g. `selectedAccountIds`, `startDate`/`endDate`, `selectedCategoryIds`, `searchTerm`, `regexSearch`) gets an explicit, typed communication path between the two components - no implicit shared mutable state. `batchCategoryInput` and everything else the batch-categorize toolbar owns stays entirely within `transaction-list`, not shared.
5. No behavior change beyond the navigation split itself: every existing handler (`loadTransactions`, `refreshTransactions`, `categorizeAllSearched`, `deleteCategoryAllSearched`, `resetCategoryChanges`, account/category selector modals, etc.) continues to work exactly as before.
6. Existing `transaction-list.component.spec.ts` tests are updated/split to match the new component boundaries rather than left broken.

## Open questions
None outstanding - resolved during refinement (see Changelog).

**Resolved**: nav trigger is a filter/search icon in `transaction-list`'s header (minimal placeholder, JIRA_13 owns the final visual design). Return flow is an explicit "Apply" action in `transaction-search` that navigates back automatically. Route/communication design (needed since sibling routes can't literally bind `@Input`/`@Output` the way a static parent-child template can): `transactions` becomes a parent route with two children - `''` (`TransactionListComponent`) and `'search'` (`TransactionSearchComponent`) - under a new thin shell component (`TransactionsShellComponent`) that hosts the child `<router-outlet>`. The shell uses the outlet's `(activate)` event to grab each activated component's instance directly, subscribes to `TransactionSearchComponent`'s `@Output() filtersApplied`, and hands the emitted filter state to `TransactionListComponent` via a public method/`@Input` when it reactivates - this is the standard Angular pattern for `@Input`/`@Output`-style communication between routed (not template) siblings, consistent with the chosen communication mechanism.

## Implementation notes

Grounded fully against the real `transaction-list.component.{html,ts,scss}` before splitting. Three real findings surfaced during implementation, beyond the two scope corrections already folded into Scope above:

1. **`account-list.component.html`'s embedded `<app-transaction-list>` was already dead code, not a real second usage.** The initial concern (flagged in Scope) was that this embedding had no way to reach a separately-routed `transaction-search`. Investigating further: `showTransactions`/`selectedAccountId`/`selectedAccountName` were never set to a truthy/non-null value anywhere except being reset in `backFromTransactions()` - the real "view this account's transactions" flow already goes through `onAccountClick()`'s `router.navigate(['/tabs/transactions'], {queryParams: {userAccountId}})`, confirmed live during `account-list`'s own `ux-apply` run earlier in this ticket's history. So instead of adding a new navigation call, the fix was simpler: **delete** the entire dead `@else` branch, `showTransactions`, `selectedAccountId`, `selectedAccountName`, `backFromTransactions()`, and the now-unused `TransactionListComponent` import from `account-list.component.{html,ts}`. `TransactionListComponent`'s own `@Input() accountId`/`@Input() groupedAccounts`/`@Output() backClicked` were removed too - nothing ever bound to them via a template once the dead embedding was gone (and `backClicked` was never even `.emit()`'d).
2. **The shell's `<router-outlet>` needed to be Ionic's `<ion-router-outlet>`, not Angular's plain one.** First pass used a plain `RouterOutlet`, which live-testing immediately caught: the header rendered at the bottom of the screen instead of fixed at top, because `ion-header`/`ion-content`'s layout depends on Ionic's own page-management CSS, which only `ion-router-outlet` wires up (position/sizing/page-transition handling). Swapped to `IonRouterOutlet` from `@ionic/angular/standalone` and the layout was correct immediately.
3. **Relative router navigation (`router.navigate(['.'], {relativeTo: ...})` / `router.navigate(['search'], {relativeTo: this.route.parent})`) failed with `NG04002: Cannot match any routes`** in live testing, despite looking correct on paper. Switched both `transaction-list`'s `navigateToSearch()` and the shell's back-navigation to plain absolute paths (`router.navigate(['/tabs/transactions/search'])` / `router.navigate(['/tabs/transactions'])`) - simpler, matches the existing `navigateToStatementUploader()` convention elsewhere in this codebase, and it worked immediately.
4. **Search term/regex toggle deliberately stayed on `transaction-list`, not `transaction-search`** - a design decision made during implementation, not in the original ticket: `searchTerm`/`regexSearch` drive `applyFilter()`, a client-side re-filter of already-fetched rows with live visual feedback as you type. Moving it to a separate route would mean typing with no visible rows to narrow, which is a real UX regression the ticket's "no behavior change" intent doesn't cover. Only the query-defining filters that trigger `TransactionService.fetchAllTransactions()` (date range, accounts, categories, DR/CR) moved to `transaction-search`.
5. **Testing note**: `TransactionsShellComponent`'s spec initially substituted a fake `Router` object via `{provide: Router, useValue: spy}`, which broke because `IonRouterOutlet` and Angular's own root `ActivatedRoute` factory both depend on a real, internally-consistent `Router` instance. Fixed by using the real `Router` from `provideRouter([])` and `spyOn(router, 'navigate')` instead of substituting the whole object - the correct pattern whenever a component under test uses `<router-outlet>`/`<ion-router-outlet>` itself.
6. **Verification**: `ng build --configuration development` clean (only pre-existing unused-import warnings, same as before this ticket). Full suite `ng test --browsers=ChromeHeadless --watch=false` - 123/123 passing (30 new/updated across `transaction-list`, the new `transaction-search`, and the new `transactions-shell` specs; the "Collapsible groups in the Select Accounts modal" tests moved from `transaction-list.component.spec.ts` to `transaction-search.component.spec.ts` along with the modal itself). Live-verified via `claude-in-chrome` against the running `local-run` stack end-to-end: clicked the header's filter icon on `/tabs/transactions` -> navigated to `/tabs/transactions/search` (seeded with the current FY dates) -> selected the `hdfc` account and widened the date range -> tapped Apply -> navigated back to `/tabs/transactions` -> skeleton rows appeared -> 123 real rows loaded. Also confirmed the live text-search box on `transaction-list` still narrows results instantly (typed "Grocery", got 1 row), and confirmed `account-list`'s "view this account's transactions" row-click still navigates correctly via the query-param path (`?userAccountId=57`) now that the dead embedded-component branch is gone.

## Addendum - wrapper composition (2026-09-11)

`ux/UX_transaction-search.md`'s Option 4 (filters and transactions on the same page, requested after this ticket's original implementation) refines this ticket's own communication mechanism rather than raising a new concern, so it's tracked here as an addendum instead of a new ticket - see that spec's Implementation detail for the full design.

**What changes**: `TransactionsShellComponent` - the `<ion-router-outlet>`/`(activate)` coordinator this ticket built specifically because `transaction-search` and `transaction-list` lived on separate routes - is deleted, along with the `/tabs/transactions/search` child route. `transactions` goes back to being a single leaf route. A new wrapper component (`TransactionsPageComponent`) composes the two as template children on one page, using the plain `@Input`/`@Output` mechanism this ticket originally chose before "separate route" forced the router-outlet detour.

**What doesn't change**: the split itself. `transaction-search` and `transaction-list` remain two separate, independently-testable components - only how they're wired together changes, not whether they exist separately. `TransactionSearchComponent.seedFilters()` becomes `@Input() initialFilters`; its `cancelled` output and back-arrow header go away (no more "screen" to cancel out of).

Real implementation findings for this addendum go here, not in a new ticket's Implementation notes, once built.

### Addendum implementation notes

See `ux/UX_transaction-search.md`'s own Implementation notes for the full write-up (content-projection composition instead of flat siblings, a live-testing-only `ion-content[fullscreen]` overlap bug, the no-Apply-button emit design, and the deliberately-left query-param-seeding gap). Summary of what changed in this codebase:
- Deleted `finance-manager-ui/src/app/transactions-shell/` and its spec.
- Added `finance-manager-ui/src/app/transactions-page/` (`TransactionsPageComponent` + spec) - a thin wrapper that projects `<app-transaction-search>` into `<app-transaction-list>`'s new `<ng-content>` slot and wires `filtersApplied` to `applyFilters()` via a template reference.
- `tabs.routes.ts`'s `transactions` entry is a single leaf route again, loading `TransactionsPageComponent`.
- `TransactionSearchComponent`: `seedFilters()` → `@Input() initialFilters`; `cancelled` output and page chrome (header, back arrow, Apply button) removed; emits `filtersApplied` on every date/DR-CR change and once per account/category modal close (if changed).
- `TransactionListComponent`: `navigateToSearch()` removed (no route to navigate to); header's filter icon removed; "No accounts selected" state's dead link removed; search bar restyled (flat underline `ion-searchbar`, `ion-toggle` replacing the bare `ion-checkbox` regex control).
- Verified: `ng build --configuration development` clean, `ng test` 124/124 passing, live `claude-in-chrome` check against the running local stack (including confirming a real HTTP request fires on a filter change via network inspection).
