# JIRA_11: `statement-onboard` skill - onboard any new statement format/bank end-to-end

**Status**: Done <!-- Draft -> In Refinement -> Ready for Dev -> In Progress -> Done -->
**Created**: 2026-09-10
**Last updated**: 2026-09-10

## One-liner
create a jira to create agent on how can we onboard .pdf version of statements for all the banks by coming up with skill that reads pdf and generates it's implementation class. We need a skill to work for any file format. It should be able to generate py code, sql inserts, etc , add unit tests, e2e tests, readme updates, architecture diagram updates. The skill should be able to onboard any new statement. It should also be able to onboard new bank. In general any statement. Also skill should document all statements configured in now in readme and keep it updated when statements are updated.

## Summary
`statement-loader` has a well-defined plugin pattern for adding a bank/broker statement format (a `StatementReader` subclass auto-discovered by `StatementReaderFactory`, keyed by `(account_id, version, extension)`, resolved at runtime via `account_statement` rows in Postgres - see `CLAUDE.md`'s "statement-loader's plugin pattern" section), but today every step of actually onboarding a new format is manual: writing the reader class, adding DB rows, writing tests, and updating docs. `account_statement` sample data already has `pdf` rows for several accounts with **no PDF reader ever implemented** (an explicit gap called out in JIRA_8's Out of scope). This ticket adds a new skill, `statement-onboard`, that automates the full onboarding workflow end-to-end for **any** file format (PDF being the immediate motivating case, not the only one) and for **any** target (a new format for an existing bank, or a brand-new bank/broker account entirely): given a sample statement dropped into a dedicated intake folder, it asks the user which bank the sample is for (from a live-queried list, via the `db-run` skill) and figures out the version itself from existing `account_statement` records - no filename convention, no metadata guessed from the file - then analyzes the file's actual content to generate the `StatementReader` implementation, the required `dbscripts` SQL (applied live via `db-run`), unit tests, e2e/BDD tests (reusing the `bdd-test-generate`/JIRA_8 patterns), README updates, and a check against `architecture-docs` (JIRA_9) for whether anything there needs updating. It also introduces (and thereafter maintains) a single "statement formats configured" reference table in `statement-loader/README.md`, kept in sync on every onboarding rather than only written once.

## Scope

### In scope
- A new skill, `statement-onboard` (a Claude Code skill, this repo's only automation primitive - not a separate "agent" type), invoked explicitly by the user, that:
  1. **Reads the dropped sample** from a new intake folder, `statement-loader/resources/onboarding_samples/` (gitignored - real personal financial data, same reasoning as `scripts/statements/`) - the filename itself is arbitrary, no naming convention or filename parsing involved. The file's actual extension (`.pdf`, `.xls`, etc.) is read directly from the file. All other metadata comes from asking the user and querying the database (steps below), never from parsing the filename or guessing from file content.
  2. **Asks the user which bank/account this sample is for**, offering the list of banks/accounts that already exist (queried live from Postgres - `account`/`account_type` - via the `db-run` skill, not hand-rolled DB access code) plus an explicit "new bank" option. For a new bank, it asks for the additional metadata that can't be looked up because it doesn't exist yet (name, account type, icon).
  3. **Determines the version itself from existing `account_statement` metadata** (again via `db-run` against the live `account_statement` table, not asked of the user or parsed from anything): for an existing bank/extension combination, the next version is one past the current highest version on record for that `(account_id, extension)` pair; for a brand-new bank or a bank's first statement in this extension, it starts at version 1.
  4. **Analyzes the sample file's actual content** (whatever format: PDF, xls, csv, xlsx, or others) to determine its structure - header/footer markers, column layout or text structure, date format, how debit/credit and balance are represented. (This is the one place file content genuinely drives the output - the parsing logic itself has to come from reading the sample; what's *not* derived from the file is onboarding metadata like bank/version, which come from the user/DB per steps 2-3.)
  5. **Generates the `StatementReader` subclass** implementing `read_statement`, `account_id`, `version`, `extension`, following the existing pattern in `service/statement_reader/{bank_savings,mutual_fund_statement}/`, and iterates against the real sample file until it parses correctly (transaction count, titles, amounts) - same "verify by actually running it" discipline as JIRA_8's fixture generator.
  6. **Generates the required `dbscripts` SQL**: new `account_type`/`account_icon`/`account` rows if onboarding a brand-new bank, and the `account_statement` row(s) mapping account + time range + extension + version to this format - added to the relevant `dbscripts/table/insert/*.sql` files (and `model/account_details_factory.py`'s `AccountDetails` enum on the Python side), and applied to the live local DB via the `db-run` skill so the onboarding is immediately usable, not just written to disk.
  7. **Generates unit tests** for the new reader (pytest, following `statement-loader/tests/`' existing conventions) and, per JIRA_8's established pattern, a *separate*, synthetic, git-committed fixture file (never the real dropped sample - the real sample stays local in the gitignored intake folder) plus a `test-automation` statement-upload + e2e_flow BDD scenario pair for the new (bank, version, extension) combination.
  8. **Updates `statement-loader/README.md`'s statement-format reference table** (new artifact this ticket introduces - see Requirements) to include the newly onboarded format, and **re-runs this update on every subsequent onboarding** so the table never goes stale.
  9. **Checks whether `architecture-docs` needs updating** (per JIRA_9's `diagram-maintain` skill/trigger conditions) - a new bank/account is a new `account_type`/`account` row, not a new table or service, so this is expected to usually be a no-op for the HLD/sequence diagrams, but the ER diagram's "Notes" section (which references concrete tables) should be checked for accuracy.
- Works for onboarding **all three** cases: a new format for an *existing* bank/account (e.g. HDFC starts also offering a PDF statement), an entirely *new* bank/broker account with no existing rows at all, and **format drift on an already-onboarded bank** - given an existing reader plus a new sample showing a changed layout, the skill updates/adds a reader for the new `version` (existing `account_statement` rows are time-bounded per version already, so this is adding a new version row + reader, not overwriting the old one - old statements must stay parseable by the version that was actually in effect for their date range).
- A new, always-current "Statement formats configured" section in `statement-loader/README.md` - one row per `(bank, account_id, version, extension)` combination currently onboarded, kept in sync by this skill (not just written once at ticket completion).
- **At least one real onboarding performed as a working demonstration** before this ticket is Done - ideally a PDF format for a bank that already has `pdf` `account_statement` sample rows with no reader (closing that specific, previously-flagged gap from JIRA_8), using a real sample the user drops into `onboarding_samples/`.

### Out of scope
- Onboarding every bank's PDF format - this ticket demonstrates the skill on one real format; onboarding the rest is follow-up work using the now-existing skill.
- Fully automatic, zero-human-input format detection for arbitrary unstructured PDFs - PDF statements vary widely in layout and often need a human to confirm column/field mapping; the skill is expected to propose a reader and iterate with the user, not silently guess and ship.
- Runtime/production PDF-parsing dependencies beyond what's needed to make the generated readers work (e.g. adding `pdfplumber`/`camelot`/similar to `statement-loader/requirements.txt` is in scope; broader OCR/scanned-PDF support is not, unless a specific bank's real PDFs need it).
- Changing the existing `StatementReader`/`StatementReaderFactory` plugin architecture itself - this skill generates code that fits the existing pattern, it doesn't redesign it.
- Automatically detecting *that* format drift has occurred (e.g. monitoring live uploads for parse failures) - the user invoking this skill with a new sample of an existing bank is what triggers the format-drift path; there's no separate drift-detection mechanism.

## Resolved (was Open questions)
- **Skill vs. "agent" wording**: delivered as a Claude Code skill (this repo's established automation primitive, same as `bdd-test-generate`/`diagram-maintain`/`healthcheck-maintain`), not a separate "agent" type.
- **Sample-file handling for personal data**: a new gitignored intake folder, `statement-loader/resources/onboarding_samples/`, holds the real dropped sample (never committed, any filename); the skill separately generates a synthetic, git-committed fixture for the test suite, extending JIRA_8's fixture-generator approach to any format including PDF.
- **Intake/metadata approach**: no filename convention and no metadata derived from the file. Bank identity is asked interactively (from a live-queried list of existing banks, with a new-bank fallback); version is derived automatically from existing `account_statement` records; file content itself is only used for the actual parsing-logic analysis, not for onboarding metadata.
- **DB access**: the skill interfaces with Postgres exclusively through the existing `db-run` skill (queries for the bank list and current max version, and applying the generated inserts) rather than writing its own database access code.
- **Demonstration requirement**: required - at least one real format must be onboarded end-to-end as proof before Done, ideally closing the existing PDF-reader gap (an account with `pdf` `account_statement` sample rows but no reader, per JIRA_8's Out of scope).
- **Format-drift/re-onboarding scope**: in scope - the skill also handles updating an already-onboarded bank when its layout changes, adding a new version/reader rather than overwriting the old one.

## Implementation notes

### What was built
- **`.claude/skills/statement-onboard/SKILL.md`**: the general-purpose onboarding skill, plus `statement-loader/resources/onboarding_samples/` (gitignored intake folder, `.gitignore` updated with a negated-pattern so its own `README.md` stays committed while everything else in it stays out).
- **Real onboarding #1 (closes JIRA_8's flagged gap)**: `HdfcSavingsAccountPdfStatementReader` (account_id=1, v1, pdf) - HDFC already had this exact `account_statement` row in sample data with no reader ever implemented; onboarding it required **zero new SQL**, just the missing Python class. Verified against the real dropped sample (`scripts/statements/HDFC.pdf`, copied into `onboarding_samples/` for this run): 114 transactions, DR=86/CR=28, matching the statement's own printed summary exactly, with a zero-mismatch running-balance replay.
- **Real onboarding #2 (format drift)**: `HdfcSavingsAccountPdfV2StatementReader` (account_id=1, v2, pdf) - a deliberately different, synthetic v2 layout (drops the ref/value-date columns, moves the opening balance to a single `OpeningBal:` line instead of a trailing summary block) to exercise the version-transition mechanics, not based on any real future HDFC change. `dbscripts/table/insert/account_statement.sql` updated and applied live via `db-run`: v1's `end_time` bounded from `9999-01-01` to a `2027-01-01` cutover, v2 starting there.
- Both readers' unit tests use **synthetic fixtures only** (`scripts/generate_dummy_statement_fixtures.py` extended with `build_hdfc_pdf`/`build_hdfc_pdf_v2`, using `reportlab`, added as a fixture-generation-only dependency like `xlwt`/`openpyxl`) - the real dropped sample never left the gitignored intake folder or got committed anywhere.
- `pdfplumber` added as a real runtime dependency (`statement-loader/requirements.txt`) for actual PDF parsing.
- `test-automation`: added `hdfc pdf v1` rows to both `upload_statement_backend.feature` and `statement_upload_to_transaction_backend.feature` (35 total scenarios now, up from 33); `test-automation/README.md` catalog updated. The v2 format-drift reader was **not** added to the BDD suite - see "Time-based resolution constraint" below for why that's correct, not an oversight.
- `statement-loader/README.md` gained the new "Statement formats configured" table (all 9 currently-implemented readers, including both HDFC pdf versions) and a Gotchas entry on the PDF quirks found.
- `architecture-docs/er/README.md` reviewed: no update needed - this onboarding added rows to an existing table (`account_statement`) and a new reader class, neither of which changes the schema/relationships the ER diagram documents.
- `model/account_details_factory.py`'s `AccountDetails.HDFC.valid_formats` updated to include `.pdf` for documentation consistency, even though (see below) this enum isn't functionally consulted.

### Real bugs/gaps found while building this
1. **`AccountDetailsFactory`/`AccountDetails` is dead code in the resolution path** - grepped for every usage; it's only ever self-referenced inside its own module. The actual `(account_id, version, extension) -> reader` resolution goes entirely through `StatementReaderFactory` + live `account_statement` DB rows. Documented clearly in the new skill and `statement-loader/README.md` rather than silently relying on it as if it mattered.
2. **`pdfplumber`'s table extraction is unreliable for this PDF's structure** (column rules, no row rules) - initially returned 0/misaligned transactions via `extract_table()`; switched to line-based `extract_text()` + regex, which correctly reproduced the statement's own summary counts (86 DR / 28 CR / 114 total) with zero balance-chain mismatches.
3. **Inconsistent space-stripping in the real PDF's extracted text** ("Statementof account" vs the header's own "Date Narration ...") caused the anchor-detection to silently match zero transactions the first time the (correctly-spaced) synthetic fixture was tested - fixed by whitespace-normalizing the anchor comparison, which then matched both the real file's quirky spacing and the fixture's clean spacing.
4. **This session's own tooling bug, unrelated to the app**: several files written earlier in this session (across JIRA_9, JIRA_10, and the start of this ticket) had a stray literal `</content>` line appended past the intended file content - caught when it caused a Python `SyntaxError` in this ticket's first new `.py` file, then found via a repo-wide grep to affect 12 files total (including some already committed/pushed in JIRA_9/JIRA_10's commits). All 12 were stripped back to their intended content; flagged here since a couple of the affected files were already live in the pushed history before this ticket started.
5. **`HdfcSavingsAccountPdfV2StatementReader`'s first draft initialized `in_table` once outside the page loop instead of resetting it per page** (unlike its v1 sibling) - a real page-count/position-independence bug the synthetic v2 fixture (single page) couldn't have caught on its own. Caught by user feedback mid-implementation to never assume fixed page counts/coordinates for PDF parsing, then found by re-comparing v2 against v1's more careful per-page reset. Fixed, and the general principle ("iterate all pages, reset per-page state per page, locate structure by content not position, test against both short and long samples of the same format") folded into the skill's PDF-lessons section for future onboardings.

### Time-based resolution constraint (why v2 isn't in the BDD suite)
`StatementReaderFactory`/`AccountStatementService` resolve a reader using the **upload's wall-clock time**, not any date embedded in the statement content - confirmed by reading `get_account_statement_mapping`'s `timestamp=datetime.now(UTC)` call site. This means only one version of a given `(account_id, extension)` can ever be live for an upload happening *now*. Setting v2's cutover in the future (2027-01-01) was a deliberate choice so the existing/new v1 BDD scenario (uploading *now*, 2026-09-10) stays correctly resolved and unaffected - proven by re-running the full 35-scenario BDD suite both before and after applying the version-transition SQL, with identical results. v2 is instead verified two ways that don't depend on real-world date having passed: (a) its own unit tests against a synthetic v2 fixture (DB-free, same as every other reader test), and (b) a one-off, live, non-committed check calling `AccountStatementService.get_account_statement_mapping(account_ids={1}, extensions={"pdf"}, timestamp=<explicit datetime>)` directly with an explicit before-cutover and after-cutover timestamp, confirming it resolves to version 1 and version 2 respectively. That check isn't part of the committed pytest suite, preserving `tests/conftest.py`'s existing "no test needs a live DB" convention (see its fake-`config_manager` docstring).

- `test-automation`: `./gradlew test` - 35/35 scenarios passed against a live local stack, run both before and after the format-drift DB change with identical results.
